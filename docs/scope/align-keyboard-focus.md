# Scope — Align keyboard focus in finding detail (#96)

## Decisions

- Reproduced against the synthetic fixture (`openApp(..., { appSource: 'fixture' })`, `typical` state, 24 h window, first finding row): both Align buttons (`#seg-align button`) are ordinary tab stops (`tabIndex 0`, visible, default Chromium `:focus-visible` ring) and Enter/Space activates them. The ticket's "never receives focus" is not a missing tab stop. inline
- What the QA reviewer saw is explained by DOM order: Align precedes the detail, so a forward pass started inside the detail never reaches it, and the reverse pass from the breadcrumb crosses all 48 basal-slot lane buttons (`#lane button`, each `tabindex=0`) before reaching Align. inline
- Confirmed defect: after keyboard activation of an Align choice, `document.activeElement` is `<body>`. `renderAlign` (`frontend/diagnose-workstation.js:356`) does `seg.innerHTML = ''` on every paint, destroying the focused button. The fix reconciles the two existing buttons in place (update `aria-pressed`) or restores focus to the button for the same key after the rebuild. → issue (#96 work order)
- The lane's 48 tab stops stay as shipped in this ticket. Ledger P27 (`mockups/finding-evidence-routing.behavior.md`) records the mock's one-tab-stop lane as a mock addition the app does not have, operator-ruled kept on 2026-08-19; changing it is a separate decision. inline (default assumed; see open question)
- Align keeps its shipped semantics: `role="group"` of `aria-pressed` toggle buttons, the same pattern as WINDOW (`#seg-window`). No radiogroup conversion and no Arrow-key roving in this ticket; the ticket's expectation is Tab reachability, a visible focused choice, and keyboard activation, all of which the toggle-button pattern provides. inline
- Add an explicit `.seg button:focus-visible` ring in `frontend/diagnose-workstation.css`, matching the accent ring its siblings already declare (`.dw button.qrow:focus-visible`, `.history-run:focus-visible`), so the focused choice is visible on the app's own terms instead of the browser default. inline
- Surface lifecycle is `revise`. Safe start: `AGENTS.md` declares `uv run harmonic serve --no-fetch --db mockups/revise-e2e.synthetic/harmonic.sqlite`, whose database is generated by `scripts/gen_revise_e2e_db.py`. Frozen ledger `mockups/finding-evidence-routing.behavior.md`; replay `frontend/diagnose-workstation-behavior.replay.mjs`. inline

### Risk contract

- **Must prevent:** Align activation changing anything it does not change today (URL, crumb level, roster, WINDOW brace); a keyboard user losing their place after choosing an alignment; regressions in the frozen ledger's replay.
- **Must recover:** none; the change is presentational and read-only.
- **Accepted failure:** the reverse keyboard path from the detail still crosses the 48 lane buttons until the lane question is ruled.
- **Unsupported:** Arrow-key movement inside Align; lane roving focus; #100 (drill-in focus) and #101 (occurrence roster keys).
- **Evidence owed:** a browser-suite story in `frontend/diagnose-workstation.browser.test.mjs` that tabs to Align, activates By event by keyboard, and asserts the pressed choice changed and focus stayed on the activated button; the frozen replay green.

Why: advisory tool, keyboard users are a real audience (accessibility label), and the fix is bounded to one control.
Disposition: inline
